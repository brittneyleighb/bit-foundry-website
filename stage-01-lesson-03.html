You write C. The processor does not execute C. This lesson follows the transformations that turn human-readable source into a running process whose machine instructions the CPU can execute.

01 / THE TRANSLATION GAP

The CPU never sees your C source.

When you write int x = 7;, that statement is meaningful to you and to the compiler. A processor works with instructions encoded for its instruction set architecture. Something has to bridge those worlds.

THE BIG IDEA

Source code is transformed into machine code before the CPU executes it. Compilation is not simply “running C.” It is a pipeline that produces artifacts at several layers.

Learning those artifacts gives you handles for debugging. Instead of treating a build as one mysterious button, you can ask which stage produced the problem.

USEFUL TERMINOLOGY

Source file → assembly → object file → executable. These are different artifacts. Later, tools such as objdump, readelf, nm, and GDB let you inspect them instead of guessing.

The syntax changes, but a causal thread remains: a value is represented, moved, stored, loaded, compared, or transformed. Low-level work becomes easier when you learn to recognize that thread across representations.

04 / FILE TO PROCESS

An executable still is not a running program.

After linking, you have an executable file. When you run it, the operating system participates in creating a process, establishing an address space, loading executable code and data, and arranging the initial execution environment.

EXECUTABLE

File stored on disk.

LOADER

Maps required program pieces.

PROCESS

Runtime state and resources exist.

MEMORY

Code and data are addressable.

CPU

Instructions execute.

This is why “compile” and “run” are different operations. One produces a program artifact; the other creates an executing instance of that program.
